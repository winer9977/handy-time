# 验证与审计记录

这份文档记录**实测过什么、怎么测的、哪些没测到**，以及逐轮地毯式审计的实锤与修复。
它不是功能介绍（那在 [README](../README.md)），而是"结论凭什么成立"的证据链 ——
公开出来一是免得后人把已修的问题再引进来，二是让读代码的人知道每条断言的判据从哪来。

写作口径：**已实测 / 已实现但未逐项实机验证 / 需要人工确认**，三者分开写，不留假绿。

- **✕ 关一次后彻底失效（用户两次报同一错误，第二次才查到真根因）**：第一次只改了 ✕ 的入口（`win.hide()` → `set_widget_visible`），没碰机制本身，于是复发。彻查后是**两个根因叠加**：
  - **根因一 · lost update（显隐被静默改回）**：前端 `saveGeometry` 换档、贴边、尺寸按钮等都发 `upsertWidget(整个陈旧快照)` **整对象覆盖**。隐藏中的挂件窗口还活着（`close` 被 `hides_on_close` 拦成 `hide`），它响应事件时用旧快照把刚设的 `visible=false` 写回 `true`。→ `upsert_widget` 对已存在挂件**保留 `visible`**（该字段只归字段级 `set_widget_visible` 管），其他字段照常更新。两条回归测试锁死。
  - **根因二 · 新建窗口不显示**：`sync_windows` 跑在命令工作线程，① `build()` 新建的窗口未必立刻进窗口表，② 的 `get_webview_window` 拿不到就静默跳过 → 窗口被创建却从不 show/attach（实测 style 缺 `WS_VISIBLE`/`NOACTIVATE`，"点了显示、store 变了、窗口不出现"）。→ 直接用 `build()` 返回的句柄就地 `apply_widget_geometry`。

## 逐轮审计记录（第 5 / 6 / 7 轮）

**第 5 轮审计（日历派生条目 / 归档口径 / 便签防抖 / PS 脚本编码）**

- **日历上"改时间"是空操作**：日视图双击日程的弹窗写着「格式 HH:MM 标题」、行的 tooltip 写着「双击改时间/标题」，但后端 `update_event` 对**派生条目**（`todo:` 前缀）只把标题写回待办，时间与重复规则被静默丢弃 —— 用户把 09:30 改成 10:00，回车后日历上还是 09:30。现在按"派生条目是待办的镜像"落三件事：标题→`title`、时刻→`remind_at` 的 HH:MM、规则→`recurrence`。两个细节：① 只在值**真的变了**时复位 `reminded`/`last_reminded_at`，否则"只改标题"会把今天已经弹过的提醒再弹一次；② 输入框是自由文本（`event-line.ts` 刻意不校验范围），而 `25:00` 写进 `remind_at` 会让 `reminder::parse_min` 解析失败、提醒**静默不响**，所以非法时刻按"这次没改时间"处理。派生条目同时也带上待办的规则，日历上这才看得出 ↻。
- **同一条待办排两次日历 = 日历上挂两条**：`todo_to_event` 每次调用都 push 新行，于是"先拖到 5 号、再拖到 8 号"在两个格子上各留一条同一待办的日程，「排到…」菜单每点一次也多留一条。改成"已有关联日程就改期"（标题/规则不动，那是排进去之后可能改过的内容），日程被 ✕ 删掉过才新建。
- **改期平移提醒漏了第 5 个入口**：看板拖列、时间线拖日直接发 `{due}`，提醒仍指着旧那天；旧那天已过则 `reminded` 还是 true，**新到期日永远不再提醒**。把"改到期日要成组带哪些字段"收进 `shared/remind.ts` 的 `duePatch`/`withDueShift`，UI 日期框 + 看板 + 时间线三处共用一份（后端同名规则是 `recurring::shift_reminders_to`，进程边界所迫无法共用代码，语义由测试对齐）。
- **归档清单的待办仍混在看板/时间线/标签计数/已完成徽标里**：`scope.ts` 的归档规则只有列表视图用了，`MainView` 的 `scoped`（喂看板与时间线）直接用 `matchScope` → 同一屏顶栏写「3 项未完成」、下面摆 5 张卡。抽出 `scopeAllowsList` 作单一定义，看板/时间线/侧栏标签/已完成计数全改走它；前端 `store.todosOf(null)`（挂件「全」）也补上排除——**注释写着"未归档"而代码没滤**，而后端 `todos_of(None)` 早就排了。

- **验证脚本自身的 4 处假绿/假红**（这轮真机跑出来的，都是脚本的错不是应用的错，记下来免得重犯）：① 探"挂件还有没有待定档"用了 `.tab`，而 `.tab` 是**清单标签页** → 永远"没有待定"的**假绿**，改用筛选按钮的真实 class `.fbtn`；② 备注断言拿了一条我以为带冒号、其实不带的条目 → 假红，改用它真实带 `: ` 的那行；③ 认日历挂件用 `.cell`，而用户把挂件停在**日视图**时根本没有 `.cell` → 假红，改成认"月/周/日三个视图按钮齐不齐"；④ "库里还留着废弃 `hotkeys`"这个探针前提会被上一次运行本身消耗掉（保存一次设置该字段就消失）→ 第二次跑必然假红，改成**每次显式塞回去**，让探针自己造得出前提。后来发现连"塞回去"都不够：应用一启动就会不断写盘，字段在**第一次保存时就消失了**，所以前提必须验在"播种之后、交给应用之前"，效果才验在后面的会话里。
- 还有第 6 处脚本缺陷值得单独记：`Start-App` 用 `return $true/$false` 报成败，但函数里那些 `Out "..."` 走的是**管道**，返回值被拼成数组 → `if (-not (Start-App))` 永远为假，CDP 起不来也照样往下跑，报出一堆误导性的"页面找不到"。改成写 `$script:cdpUp` 标志位。
- 同时**纠正我上一轮写错的一条结论**：当时写的是"同一脚本里第二次起的实例，应用活着但 WebView2 不起 CDP 端口，属环境/会话问题"。真因后来查清了，而且根本不是 bug：**CDP 端口属于 WebView2 的浏览器进程，浏览器进程只在有可见窗口时才存在**。用户库里三个挂件都是 `visible=false`（13:54 自己收起来的），第二个会话加载真实库 → 零个 webview → 端口当然不监听；第一个会话能连上，只是因为脚本播种的一次性库强制 `visible=true`。两条教训：① 断言失败先问"前提还在不在"，别急着归因环境（我当时差点把"应用起不来"写进 README）；② 依赖 CDP 的检查必须自带"有没有可见窗口"这一路判据，否则"没端口"和"应用坏了"长得一模一样。T9 改用文件级判据（进程活着 / 没有 `store.corrupt-*` / 日志无解析失败 / 待办条数不变）依然成立，但理由要换成这一条对的。
